Incident Copilot Architecture

An assistant for on-call engineers. When an alert fires on Kubernetes, it looks around, works out what broke, and suggests one fix. A human must approve a risky fix before anything changes. The rule behind the whole design: the AI figures out what is wrong, ordinary code decides what happens next and who may approve, and Kubernetes decides what that person is allowed to change.

The big picture

There are two areas. Docker Compose runs our side: the web API (with the LangGraph flow inside it), Postgres, Keycloak for logins, and Jaeger for traces. The kind cluster is the "patient": a small Kubernetes cluster running deliberately broken apps, plus three tool servers that are the only way in.

The API has no Kubernetes password of its own. It passes the logged-in person's ID card (token) to the tool servers, and they act in Kubernetes as that person.

Tech stack

Everything is open source except the AI model (DeepSeek) and the optional AI run viewer (LangSmith). One theme runs through the choices: the whole path is async. One Python process can wait on many slow things at once (AI calls, tool calls, live browser feeds) without getting stuck.

Is it ASGI? Yes. What does that mean?

ASGI (Asynchronous Server Gateway Interface) is the agreement between a Python web server and a Python web app about how requests are handed over. Here the server is Uvicorn and the app is FastAPI. The older agreement, WSGI (used by classic Flask and Django), ties up one worker per request until the response is finished. ASGI lets one process juggle many requests: while one request waits, the process works on others.

AnalogyA WSGI waiter stands at your table until your food arrives. An ASGI waiter takes your order, serves other tables, and comes back when the kitchen rings the bell.

Why it matters here: an incident run spends most of its time waiting. A DeepSeek reply takes seconds, a tool call goes over the network, verify polls for 45+ seconds, and every open incident in the browser keeps a live feed (SSE) connected for minutes. With WSGI, each of those would hold a worker for the whole time. With ASGI, a single Uvicorn process handles all of them. The graph runs themselves are background tasks on the same event loop, and every layer below is async too:

browser ──HTTP/SSE──▶ Uvicorn (ASGI server) ──▶ FastAPI (async routes)
                                                  └─▶ LangGraph astream()   ── background task per run
                                                       ├─▶ psycopg (async)   ── Postgres
                                                       ├─▶ httpx (async)     ── MCP tool servers
                                                       └─▶ DeepSeek client   ── AI calls

The one place we had to care: on Windows, async psycopg needs a "selector" event loop. Local scripts set it explicitly (run_async in config.py). The API runs on Linux in Docker, so it doesn't need that.

The main flow

Nine steps. The middle one, supervisor, works like a traffic controller: every agent reports back to it, and it sends the work to the next stop. It is plain Python with no AI in it. (Why that works is answered in your questions.)

Inside an agent

All three agents are built from the same template. The AI gets the look-only tools and loops: think, call tools, read the results, think again. Each agent has a limit on how many rounds of tool calls it may make. When it stops, a last step called conclude makes it fill in a fixed form (for triage: severity, is it real, summary). Code can then read that form reliably.

Diagnosis is special. First it asks the AI for up to 3 possible causes. Then it starts one investigator per cause, at the same time, like three doctors testing three theories in parallel. Finally it reads their verdicts and names the cause.

Agents and AI calls

Three agents use tools. Because the investigator runs once per suspected cause, up to three of them can work at the same time. Three more steps are single AI calls that just fill in a form, with no tools. The supervisor uses no AI.

The cause category comes from a fixed list: oom (out of memory), cpu_saturation, dependency_down, bad_config, bad_image, no_issue, unknown. A fixed list means code can route on it, tests can grade it, and remediation can pick the matching runbook.

Tools

The AI can look with 6 tools. It cannot change anything itself. For a change it can only write a request on a form ("roll back checkout-api to version 1"). Only one step, execute_action, can carry out such a request, and it sits after the approval gate. So there is no path where a change skips the gate.

In plain wordsThe AI is like a junior doctor who can examine the patient and write a prescription, but cannot open the medicine cabinet. Only the pharmacist can, and only with a signed prescription.

  • The AI never writes database or metrics queries. It picks a metric by name ("memory_usage") and the server builds the query, and only for the caller's own company.
  • Tools never get "who am I" from the AI. The user's identity is handed to tools by our code (LangGraph's runtime context), so the AI cannot pretend to be someone else.

Approval, step by step

This is the live out-of-memory incident: alice opens it, bob approves the fix. All the checks before the flow continues are ordinary Python in the API. The flow then checks again on its own.

Safety layers

Any one of these layers would stop a wrong change on its own. They are stacked, like several locks on one door, so a bug in one is caught by the next.

  1. Keycloak hands out ID cards (tokens). Each token says who you are, your company, and your roles (sre, or also sre-approver).
    infra/keycloak/realm-incident-copilot.json
  2. The API checks the ID card is genuine and not expired. You only ever see your own company's incidents. Another company's incident looks "not found" instead of "forbidden", so you can't even tell it exists.
    auth/jwt.py · auth/rbac.py
  3. Before the flow continues, the API checks the approver: has the approver role, same company, isn't the person who opened the incident (the four-eyes rule), the incident really is waiting for approval, and the fingerprint matches what is waiting.
    approval/service.py
  4. The approval covers one exact action. The fingerprint is made from the action, the incident and the company. Approving "roll back checkout-api" can't be reused for a different action or incident.
    approval/hashing.py
  5. The gate checks the fingerprint again when the flow continues. Even if the API had a bug, a mismatched approval is refused inside the flow.
    graph/gate.py · approval_gate
  6. The executor looks for the 'approved' row in the audit log before doing anything, and records 'blocked' if it's missing. If an 'executed' row already exists, it does nothing, so the fix never runs twice, even after a crash.
    graph/gate.py · execute_action
  7. The tool server checks the ID card itself. Then it tells Kubernetes "act as kc:bob, member of acme". Only the change server, and only for approvers, adds "member of acme approvers".
    mcp_servers/common.py
  8. Kubernetes applies bob's permissions. Approvers may change apps only in their own company's namespaces. The tool servers' own accounts can do nothing except "act as" a short list of names. Kubernetes' own log records both the tool server and bob.
    infra/kind/manifests/10-rbac.yaml
  9. The audit log is written in ink. The app's database account is not allowed to edit or delete rows, a database trigger blocks it as well, and each row contains a fingerprint of the row before it. Changing an old row breaks the chain, and a check script finds where.
    infra/postgres/schema.sql · approval/audit.py

Your questions

1. The supervisor routes in code, with no AI. How does that work?

The AI is still involved. It just isn't the one choosing the next step. Each agent ends by filling in a fixed form (structured output). Triage's form has a yes/no box called actionable. Diagnosis's form has a category from the fixed list and a confidence of low, medium or high. Remediation's form either contains an action or doesn't.

The supervisor is a short Python function that reads those boxes, top to bottom, and returns the first matching rule. A simplified version of next_step in graph/supervisor.py:

if no triage yet:                         go to triage
if triage.actionable is False:            go to finalize     # false alarm
if no diagnosis yet:                      go to diagnosis
if diagnosis.category == "no_issue":      go to finalize
if confidence is low and attempts < 2:    go to diagnosis    # try new theories
if still unsure after 2 attempts:         go to finalize     # hand to a human
if no remediation yet:                    go to remediation
if a fix was proposed:                    go to approval_gate
otherwise:                                go to finalize     # no safe fix

It returns the choice to LangGraph as Command(goto="diagnosis"), which is how a node says "run that step next".

AnalogyThe doctors examine the patient and fill in the chart. The flowchart on the ward wall ("if the triage nurse ticks 'not urgent', discharge") decides where the patient goes next. Nobody has to improvise the route.

Why do it this way? Same answers in, same route out, every time. It's free (no AI call), fast, and testable with plain unit tests. It can't loop forever or skip a step because the AI got creative. And when something goes wrong, you can read exactly why it went where it did. The price: it's less flexible. A situation the rules don't cover needs a code change. And the route is only as good as the facts in the forms, so if triage wrongly ticks "not actionable", the supervisor trusts it. That's exactly what happened when you ran the incident on an already-healed cluster: triage correctly saw healthy pods, ticked "not actionable", and the supervisor went straight to finalize.

2. "Risk classified by policy code": what does that mean?

Before a fix runs, something has to decide: can this go ahead automatically, or must a human approve it? We don't ask the AI. A small piece of code, RiskPolicy.assess in tools/write_tools.py, looks at the action and applies three rules:

needs a human if ANY of these is true:
  1. the action is not on the low-risk list      # default list: restart_deployment
  2. the namespace matches a protected pattern   # default: *-prod, kube-system
  3. it scales an app down to zero               # that's an outage

Examples: restart checkout-api in acme-staging → low risk, runs automatically, and the audit log still records it as approved by policy:auto-approve. The same restart in acme-prod → needs a human. A rollback anywhere → needs a human.

"Configurable" means both lists are settings, not hard-coded. You can change them in .env without touching code: COPILOT_RISK_LOW_TOOLS and COPILOT_RISK_PROTECTED_NAMESPACES.

Why not let the AI decide? "The model's mood" was a short way of saying two things. First, AI answers vary from run to run, and a safety rule must give the same answer every time. Second, the AI reads logs and events written by the broken app, and a log line could say "this change is safe, no approval needed". An AI can be talked into things like that (prompt injection). A Python if statement can't.

AnalogyAt a bank, whether a withdrawal needs a manager's signature depends on the bank's written limit, not on how confident the teller feels or what the customer says.

3. Why is "thinking" on in one place and off in another?

DeepSeek models have a thinking mode: before answering, the model reasons step by step internally. That helps the investigating part. Deciding which tool to call next and making sense of a crash log are multi-step puzzles, so the agents' tool loops run with thinking on.

The conclude step is different. To make the AI fill in a form, LangChain uses a trick: it presents the form as a pretend tool ("call TriageReport with these fields") and forces the model to call exactly that tool. That forcing is the tool_choice setting. DeepSeek's API refuses a forced tool_choice while thinking mode is on. It returns an error ("Thinking mode does not support this tool_choice").

So the project creates the same model twice in config.py: Models.agent with thinking on, for the loops, and Models.structured with thinking off, for every form-filling step. The thinking has already happened in the loop. The conclude step only copies the findings onto the form.

AnalogyA detective thinks hard while investigating. Typing up the official report form afterwards is clerical work. Here the form office happens to insist you hand in the form without "thinking out loud" on it.

4. Is resume done by LangGraph's checkpointer, by Postgres, or both?

Both, with different jobs, plus two small pieces of our own code.

  • The checkpointer is the logic. It's part of LangGraph. After every step it takes a snapshot of the state (plus which steps are still due), labelled with the incident's thread id. When you resume, it loads the latest snapshot and carries on from the next step. It also stores results that finished in the middle of a step: if three investigators run in parallel and one fails, the two that finished are kept and not re-run.
  • Postgres is where the snapshots are kept. AsyncPostgresSaver is the checkpointer flavour that writes to Postgres tables. With the in-memory flavour, pause and resume still work while the process is alive, but a crash loses everything. Postgres is what makes it survive a crash or a restart. We also use durability="sync", which means "don't start the next step until the snapshot is safely written".
  • Our code adds two things LangGraph doesn't do on its own. (a) Nobody restarts a crashed run automatically: when the API starts, it marks runs that were in progress as interrupted, and someone calls POST /incidents/{id}/resume. (b) LangGraph restarts an unfinished step from its beginning, so a step with side effects must be safe to repeat. That's why the executor checks for an executed audit row before applying a fix.
AnalogyThe checkpointer is the habit of saving your game after every level. Postgres is the memory card. Without the card, the save disappears when the console switches off.

5. Is this the same as Temporal?

Same idea, lighter tool. Both give "durable execution": a long process that survives crashes and can wait days for a person. Here are the differences:

In short: we built Temporal-style durability for an AI agent, saved after every step, with a manual restart. For one API process that's enough, and it was tested by killing a run after diagnosis and resuming it without repeating triage. With many machines and automatic restarts there are two usual options: LangGraph's hosted platform, which adds a run queue, or running the LangGraph flow inside a Temporal workflow.

  • This is how bob executes alice's incident. On resume the API passes a new context with bob as the actor. The state (the incident) stays the same, but the identity changes. Investigation ran as alice, and the fix runs as bob.

StateGraph, nodes and edges

A flowchart where each box (node) is an ordinary async Python function and arrows (edges) say what runs next. A node returns only the fields it changed, and LangGraph merges them into the state.

Here: 9 nodes in graph/build.py; fixed edges such as verify → finalize.

builder.add_node("verify", make_verify(settings), retry_policy=TOOL_RETRY)
builder.add_edge("verify", "finalize")
builder.add_edge("finalize", END)

Reducers

They say how to combine two writes to the same field. The default is "replace". add_messages appends chat messages, and operator.add appends to a list.

Here: three investigators each return {"verdicts": [one]} at the same time, and the reducer keeps all three (graph/state.py).

verdicts: Annotated[list[dict], operator.add]
messages: Annotated[list[AnyMessage], add_messages]

Subgraphs with input/output schemas

A compiled graph used as one node. The input schema limits what it reads from the parent, and the output schema limits what it hands back. Its chat history stays inside.

Analogy: a contractor gets a brief and returns a report, and keeps their scratch notes. Here: triage, diagnosis, investigator and remediation (graph/agents.py).

StateGraph(DiagnosisState, input_schema=DiagnosisInput,
           output_schema=DiagnosisOutput)
builder.add_node("diagnosis", build_diagnosis(models, settings))

Command(goto) and destinations

A node returns "go to X next", and can update the state at the same time. destinations lists the possible targets, so the graph can still be drawn and checked.

Here: the supervisor and the approval gate (graph/supervisor.py, graph/gate.py).

return Command(goto="execute_action",
               update={"approval": approval})
builder.add_node("supervisor", supervisor,
    destinations=("triage", "diagnosis", "remediation",
                  "approval_gate", "finalize"))

Conditional edges

A small function looks at the state and picks the next node.

Here: after the change runs, go to verify if it executed, otherwise to finalize.

def after_execute(state):
    return "verify" if state["execution"]["status"] == "executed" else "finalize"
builder.add_conditional_edges("execute_action", after_execute, ...)

Send: run copies in parallel

Starts several copies of one node in the same step, each with its own input.

Here: one investigator per suspected cause (graph/agents.py).

def fan_out(state):
    return [Send("investigate", {"alert": ..., "hypothesis": h})
            for h in state["hypotheses"]]
builder.add_conditional_edges("propose", fan_out, ["investigate"])

interrupt() and Command(resume)

interrupt(payload) pauses the run and saves everything. Later, any process continues it with Command(resume=value), and interrupt() returns that value inside the node.

Here: the approval gate pauses with the action and its fingerprint, and the API resumes with bob's decision. Worth knowing: the paused node re-runs from its start on resume, so everything before interrupt() must be safe to repeat.

decision = interrupt({"type": "approval_request",
                      "action": payload, "action_hash": digest})
# API, later:
graph.astream(Command(resume={"decision": "approve", ...}), config)

Checkpointer and thread_id

Saves a snapshot after every step under a thread_id (one per incident). It's required for interrupt, and it gives crash recovery. durability="sync" waits for each save before the next step starts.

Here: AsyncPostgresSaver (db.py); a run killed after diagnosis resumes without repeating triage.

config = {"configurable": {"thread_id": "inc-1e95..."}}
graph.astream(inputs, config, durability="sync", ...)

State history and time travel

List every snapshot of a thread, re-run from an old one, or change one and branch off a new path.

Here: scripts/history.py (--replay, --fork) and the Checkpoints tab. Good for asking "what if diagnosis had said X?"

async for snap in graph.aget_state_history(config): ...
config = await graph.aupdate_state(config, update, as_node="triage")

RetryPolicy

Retries a node automatically on chosen errors, waiting longer each time.

Here: tools, the executor and verify retry up to 4 times, only on TransientBackendError. AI steps retry 3 times on API errors or a badly filled form. Errors like "forbidden" go back to the AI instead (graph/common.py).

TOOL_RETRY = RetryPolicy(max_attempts=4, initial_interval=0.2,
                         backoff_factor=2.0, retry_on=TransientBackendError)

Streaming

updates: what each node changed. messages: AI tokens as they arrive. custom: our own events, sent from inside nodes. subgraphs=True: also include events from inside subgraphs.

Here: it feeds the live timeline in the UI over SSE (runner.py).

graph.astream(..., stream_mode=["custom", "updates", "messages"],
              subgraphs=True)
runtime.stream_writer({"type": "route", "to": goto, "reason": reason})

Store: long-term memory

Memory that outlives one incident, organized by namespace.

Here: past incidents and runbooks, with a separate namespace per company so acme and globex never mix (memory/store.py).

await store.asearch(("tenants", t, "incidents"), filter={"service": svc})

Masking: what leaves the system, and how it's cleaned

Data leaves our process in four directions: trace timelines to Jaeger, AI run recordings to LangSmith, prompts to the AI model (DeepSeek), and everything we save in Postgres. Each gets different treatment, so first, why there are two trace viewers at all.

The cleaning rules

There is one list of four patterns, _PATTERNS in observability/tracing.py, and one function, redact(), that applies them to text. Both trace destinations use the same list, so a rule added once applies everywhere.

How each destination is protected

Jaeger: cleaned at the exit door

All spans leave the API through one exporter. We wrap it in RedactingExporter. Finished spans are read-only, so for each span it hands the real exporter a cleaned copy, with every attribute and event value passed through redact().

Cleaning at the exit means nothing can slip past. That includes spans we didn't write ourselves, such as FastAPI's request spans and httpx's outgoing-call spans, which can carry URLs and headers.

On top of that, our spans carry very little: step names, timings, tool names, a 500-character preview of tool arguments (cleaned again when the span is created), and token counts. No prompt text and no tool results are ever put on a Jaeger span. The user is tagged by their Keycloak id (a random UUID), never their username or email.

LangSmith: cleaned before upload

LangSmith records full prompts and tool results, so cleaning matters more here. Every run starts inside langsmith_masking() (in runner.py). It swaps in a LangSmith client built with an anonymizer made from the same four patterns. The client runs every string in the inputs and outputs through it, including nested values, before anything is uploaded.

LangSmith's rules take a plain replacement text, so the "password=…" rule replaces the whole match with <redacted> (the setting's name is masked too).

Checked on 2026-11-22: LangChain's tracer uses this masked client, and the client masks a sample with an email, a bearer token, a JWT and DB_PASSWORD=… in nested inputs and outputs. Not yet checked by opening a real run in the LangSmith web UI.

AnalogyIt's like a mailroom that blacks out sensitive lines on every letter as it leaves the building, rather than trusting each writer to remember. Writers are also asked to keep letters short in the first place.

Protection at the source

  • Secret settings never leave Kubernetes. When a tool describes a pod, settings that come from a Kubernetes Secret or ConfigMap are shown as <from secret/configmap>. The AI, the traces and LangSmith never see those values at all (mcp_servers/k8s_format.py).
  • The login token is never stored or printed. It travels in LangGraph's runtime context, not in the state, so it's never written to a checkpoint or included in a run's recorded inputs. On the Actor object it's marked repr=False, so it doesn't show up when the object is printed or logged.
  • Secrets stay out of git. API keys live in .env, which is in .gitignore. .env.example has empty values.
  • Tests cover it: test_exporter_masks_pii and test_redact_jwt_and_secrets in tests/unit/test_tracing.py.

What is not masked

  • What the AI model receives. Prompts sent to DeepSeek include raw tool results: pod logs, events, and settings written directly into a deployment (not via a Secret). If an app logs a password, the model sees it. Masking is only applied to the trace viewers. Cleaning tool results before they reach the model would close this, at some risk of hiding clues the diagnosis needs.
  • The tool servers' own spans. The MCP servers send spans to Jaeger directly, without the redacting exporter. They contain no prompts or results, but they do carry the impersonated user (kc:alice). With demo users that's a plain name. If usernames were email addresses, they would reach Jaeger unmasked.
  • Patterns only catch known shapes. Names, phone numbers, IP addresses or a custom token format aren't caught. Regex masking lowers risk; it doesn't guarantee privacy.
  • Our own database. Checkpoints and the audit log store results and action details as they are. That's our own storage, protected by database permissions rather than masking. A set_env action that sets a secret value would be stored in plain text there.

Testing

Two kinds of tests, kept apart on purpose. The safety parts (approval, roles, audit) get normal tests that must pass every time, because "usually blocks an unapproved change" isn't good enough. The AI's judgement gets evals that run each scenario several times, because one run tells you little.

109 normal tests

They use a scripted fake AI and need no API key. They cover the approval gate (wrong fingerprint, missing audit row, double approval, no double execution after a replay), roles and companies, token checks, a tampered audit chain, database permissions, resume after a crash, the tool servers' identity rules, the "healthy for 45 s" rule, and masking in traces.

Evals: 6 fake incidents × 3 runs

Real AI with recorded tool answers. Each run is graded on the cause category, the proposed fix (right action, right app), whether the fix worked, and the path taken: required tools used, within the tool-call budget, nothing executed without an approval row.

Shortcuts that would change in production

  • The same token goes all the way to the tool servers. Production would swap it for a narrower token at each hop (OAuth "token exchange", RFC 8693).
  • One API process. Runs happen as background tasks inside the API. Several copies of the API would need a shared job queue. The save points already let any copy resume a run.
  • Keycloak runs in development mode with demo users and passwords.
  • The metrics tool server keeps companies apart. Production would put that rule in a proxy in front of Prometheus, or use a metrics store that supports multiple companies.
  • The fake incidents have clear clues. Harder ones (misleading clues, two problems at once) would make the evals more useful.
  • Masking covers the trace viewers, not the AI model. Tool results reach DeepSeek as they are, and the MCP servers' spans skip the redacting exporter. See Masking for the full list.
